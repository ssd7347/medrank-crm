1. Executive Summary
This document is the single, complete specification for a Customer Relationship Management (CRM) system built
for an MBBS/BDS admission counselling consultancy operating in the domestic India NEET counselling
ecosystem — guiding NEET-qualified candidates through college selection, choice filling, seat allotment,
document verification, and admission confirmation across All India Quota (MCC), State Quota, Management
Quota, and NRI Quota.
It consolidates every module and every requirement discussed across the full planning process into one place: 15
core operational modules, 10 advanced/AI-driven modules, 3 financial/legal-risk modules, and the newest
addition — Module 29, an AI Voice Calling Agent — documented here not just as a feature description but as a
complete, developer-ready build specification (Section 18), including architecture, API contracts, database
schema, conversation design, compliance requirements, and an implementation task backlog.
The system must handle two very different operating modes: a calm, moderate-load mode most of the year, and
an extreme, predictable-but-brief spike mode during live counselling rounds, when thousands of students check
results and must make binding decisions within hours. Every architectural decision in this document, including the
voice agent's design, is made with that second mode as the harder constraint.
2. Project Objectives
l
Centralize every student inquiry into one lead pipeline, from first contact to confirmed admission.
l
Maintain an accurate, continuously updated database of MBBS/BDS colleges, seat matrices, quota-wise fee
structures, and historical cutoff ranks.
l
Give students a reliable, disclaimer-backed rank-based college predictor grounded in historical data.
l
Track each student's parallel applications across AIQ (MCC) and their home-state counselling authority.
l
Never miss a deadline: automated, high-priority alerts and, where appropriate, AI-driven voice calls for
choice-filling windows, result releases, document verification, and reporting dates.
l
Manage the full document checklist and verification status, with government-source auto-verification where
possible.
l
Give management real-time visibility into lead conversion, counselling-round outcomes, and revenue.
l
Support a distributed team: counsellors, telecallers, documentation staff, and referral associates/agents.
l
Remove manual bottlenecks with automation: AI-assisted qualification, auto-fetched documents, predictive
prioritization, and AI-assisted phone calls for routine, high-volume conversations.
l
Protect students and the firm from costly, avoidable mistakes around seat-withdrawal timing, refund eligibility,
and loan-approval delays.

Auto-flag AIQ vs. State Quota vs. Deemed/Central university eligibility based on domicile and category rules.

Master list of MBBS/BDS colleges with location, affiliation, NMC recognition status.

4.16 DigiLocker Integration (Auto-Verified Documents)
Purpose: Removes the biggest manual bottleneck and fraud risk in Module 4.7.
Features:
l
Consent-based fetch of government-issued documents (Aadhaar, marksheets, category/domicile certificates)
directly from DigiLocker.
l

Falls back to manual upload/verification for any document not yet available via DigiLocker.

Requires DigiLocker API credentials/license and an approved integration with the relevant issuing departments.

Hands off to a human counsellor once qualified, with full context already captured in the lead record.
l
AI-assisted prioritization surfaces which leads/students a counsellor should act on next.
l
Text-channel counterpart to the AI Voice Calling Agent (Module 29); shares the same FAQ knowledge base.

Scores active students on drop-off/dissatisfaction risk (missed calls, delayed payments, unresolved tickets).

4.29 AI Voice Calling Agent (Outbound & Inbound)
Purpose: An AI-powered voice agent that places and receives phone calls, speaks naturally with students and
parents, pulls live CRM data mid-conversation to answer accurately, clarifies doubts, and logs the full
conversation back into the CRM. See Section 18 for the complete developer-ready build specification
(architecture, API contracts, database schema, conversation design, compliance, and implementation task
backlog).
Features:
l
Outbound calling: deadline reminders, missing-document nudges, fee-due reminders, missed-call follow-up,
new-lead qualification.
l
Inbound calling: after-hours FAQ handling, routine status checks, initial lead qualification.
l
Live context lookup mid-call via a secure Tool API (deadlines, round status, allotment summary, document
status, fee status, predictor results, FAQ).
l
Hard-blocked from advising on or confirming withdraw/accept/upgrade decisions and from handling
grievance/dispute calls — both are always routed to a human counsellor.
l
Tiered identity verification before any personal data is shared on a call.
l
Full call recording, transcript, and outcome logging tied to the student record.
l
Tamil/Hindi/English support via Module 25.
l
TRAI/DLT-compliant consent, DND scrubbing, and calling-window enforcement.

6.1 Stack Decision Notes
l
Use Flyway or Liquibase for versioned database migrations from day one.
l
Start as a modular monolith (one Spring Boot app, clear packages per module, including a dedicated
voiceagent package — Section 18.7). Isolate the alert-dispatch pipeline and the AI/voice services early; both
have different load/latency profiles from the rest of the system.
l
Avoid building a custom WhatsApp/SMS/voice gateway; use established BSPs/platforms to stay compliant with
messaging and telecom policies.
l
Treat the college/seat-matrix/cutoff/refund-rule dataset as a first-class asset with its own change-approval
workflow.
l
DigiLocker, Aadhaar e-Sign, telephony, and voice-platform integrations each require their own
registration/approval process; budget lead time before Phase 5.

7. High-Level System Architecture
l
Client Layer: Web app (React/Next.js) for staff; PWA/React Native app for students and parents with
push-notification support.
l
API Gateway / Backend: A single Spring Boot application organized into packages covering all 29 modules,
each with its own Controller, Service, and Repository layer.
l
Alert Pipeline (isolated): A Kafka/RabbitMQ event pipeline firing the moment an allotment result or deadline
event occurs, fanning out to WhatsApp/SMS/push/voice-call triggers on a priority queue, decoupled from the
core API.
l
Voice Agent Layer (isolated, new in this version): A telephony provider (Exotel/Knowlarity) paired with a
voice AI orchestration platform (Retell AI/Vapi/Bland), which calls Claude as the reasoning model and calls
back into our backend's Tool API for live data. See Section 18 for full detail.
l
AI/Scoring Service (isolated): A small microservice serving the chatbot and lead-scoring/drop-off models,
called by the core backend over REST.
l
Background Workers: Spring Batch jobs for scheduled reminders and nightly data-consistency checks.
l
Database Layer: PostgreSQL as the system of record; Redis caching the college/predictor read-path.
l
Storage Layer: S3/R2 for uploaded documents, DigiLocker-fetched documents, and voice-call recordings.
l
Integration Layer: Dedicated adapters for payment, WhatsApp BSP, SMS, email, DigiLocker, Aadhaar e-Sign,
video conferencing, telephony/IVR, NBFC loan partners, and the voice AI platform — each swappable without
touching core business logic.
l
Admin/Reporting Layer: Metabase connected read-only to the production database (or a replica).

18. Module 29 — AI Voice Calling Agent: Full Developer Build
Specification
This section is the complete, standalone build specification for Module 29, included here in full so that every
feature and every implementation detail of the CRM lives in this one document. It is written for developers (and
for Claude Code) to build directly from.
Anything marked [VERIFY] depends on a third-party platform's current documentation or on legal advice
and must be confirmed before coding against it.
18.1 Overview, goals and non-goals
The AI Voice Calling Agent lets the consultancy automate phone conversations with students and parents. The
agent places outbound calls (reminders, nudges, qualification) and answers inbound calls (status questions,
FAQs). During a call it can look up the caller's live CRM data, answer questions in plain spoken language (Tamil,
Hindi or English), and hand the call to a human counsellor when needed. Every call is logged back to the student
record.
18.1.1 Goals
l
Reduce manual call load on telecallers/counsellors for routine, high-volume conversations.
l
Ensure no critical deadline (choice filling, decision window, document verification, reporting date) goes
unreminded.
l
Answer routine questions 24/7 with information taken only from CRM data, never invented.
l
Capture every call (transcript, summary, outcome) against the student record for counsellor follow-up.
l
Stay compliant with Indian telecom and data-protection rules (Section 18.14).
18.1.2 Non-goals (explicitly out of scope for v1)
l
Making or confirming irreversible decisions for a student (accept / withdraw / upgrade a seat). Humans only.
l
Handling active grievances or fee disputes. Auto-escalate to a human and the Grievance Register (Module 28).
l
Cold calling people who have not given contact consent.
l
Giving admission-outcome guarantees. The agent may read out predictor results only with the estimate-only
disclaimer.
l
Building our own speech-to-text, text-to-speech or telephony stack (use a managed voice platform).

18.3 Key design principles
l
Grounded answers only. The agent states facts about a student only if returned by a tool call in this call. If a
tool fails, it says it cannot check right now and offers a callback. It never guesses.
l
Server-side authorization. The AI never supplies a student ID. The backend resolves the student from the call
ID it issued. A caller (or prompt-injection) cannot request another student's data.
l
Tiered disclosure. Until identity is verified (Section 18.12), the agent says nothing personal beyond a generic
reminder.
l
Least data to the model. Send only fields needed for the call purpose, never full profiles, documents, Aadhaar
numbers or payment data.
l
Humans own irreversible decisions. Accept/withdraw/upgrade, refunds, disputes always route to a
counsellor.
l
Disclose that it is an AI at the start of every call and, where recording is on, that the call is recorded.
l
Everything is logged to the Communication Log and a dedicated voice_call table.

Tool responses are minimal DTOs. Never return the entity. Never return Aadhaar, full DOB, address, full phone,
payment instrument or document images.

l

l
Write an audit record for every tool invocation (call_id, tool, args hash, result status, latency).

A.1 HMAC verification filter (Spring Boot 3, Java 21)
Wrap the request so the raw body can be read twice (e.g. ContentCachingRequestWrapper) and compare
signatures in constant time.
@Component
public class VoiceSignatureFilter extends OncePerRequestFilter {
  private final byte[] secret;
  public VoiceSignatureFilter(@Value("${voice.hmac.secret}") String s) {
    this.secret = s.getBytes(StandardCharsets.UTF_8);
  }
  @Override protected boolean shouldNotFilter(HttpServletRequest r) {
    return !r.getRequestURI().startsWith("/api/v1/voice/tools")
        && !r.getRequestURI().startsWith("/api/v1/voice/webhooks")
        && !r.getRequestURI().startsWith("/api/v1/voice/inbound");
  }
  @Override protected void doFilterInternal(HttpServletRequest req,
        HttpServletResponse res, FilterChain chain) throws IOException, ServletException {
    var wrapped = new CachedBodyRequest(req);          // custom wrapper, re-readable body
    String header = req.getHeader("X-Voice-Signature");
    String ts = req.getHeader("X-Voice-Timestamp");
    if (header == null || ts == null || tooOld(ts) ||
        !constantTimeEquals(header, "sha256=" + hmacHex(wrapped.body()))) {
      res.sendError(401); return;
    }
    chain.doFilter(wrapped, res);
  }
  private String hmacHex(byte[] body) { /* HmacSHA256 with secret -> hex */ return ""; }
  private boolean tooOld(String ts) { return Math.abs(Instant.now().getEpochSecond()
                                        - Long.parseLong(ts)) > 300; }
  private boolean constantTimeEquals(String a, String b) {
    return MessageDigest.isEqual(a.getBytes(), b.getBytes());
  }
}
A.2 Tool controller and handler skeleton
@RestController
@RequestMapping("/api/v1/voice/tools")
class VoiceToolController {
  private final ToolRegistry registry; private final CallContextService ctxSvc;
  @PostMapping("/{tool}")
  ToolResponse invoke(@PathVariable String tool, @RequestBody ToolRequest body) {
    CallContext ctx = ctxSvc.resolve(body.callId());       // call_id -> student/lead, level
    ToolHandler h = registry.get(tool)
        .orElseThrow(() -> new UnknownToolException(tool));
    long t0 = System.nanoTime();
    try {
      if (h.minLevel() > ctx.verificationLevel())
        return ToolResponse.error("VERIFICATION_REQUIRED",
                                  "Ask the caller to verify identity first.");
      return h.handle(ctx, body.args());                   // never reads student id from args
    } finally {
      audit.record(ctx.callId(), tool, body.args(), System.nanoTime() - t0);
    }
  }
}
interface ToolHandler {
  String name();
  int minLevel();                                          // 0 or 1
  ToolResponse handle(CallContext ctx, JsonNode args);
}
@Component
class GetDeadlinesHandler implements ToolHandler {
  public String name() { return "get_deadlines"; }
  public int minLevel() { return 0; }                      // generic at 0, personal at 1
  public ToolResponse handle(CallContext ctx, JsonNode args) {
    var list = ctx.verificationLevel() >= 1
        ? deadlines.forStudent(ctx.studentId(), 3)
        : deadlines.generalUpcoming(3);                    // no personal data at level 0
    return ToolResponse.ok(list.stream().map(DeadlineDto::from).toList(),
                           "Your next deadline is " + list.get(0).spoken());
  }
}
